> 版本：1.0（2026-10-02）

## 1. 项目定位

### 1.1 一句话定义

把一份订单农业合同 PDF，变成「**可核验的结构化信息 + 对应标准依据 + 风险推演**」。

### 1.2 核心命题：什么是"可信"

订单农业的核心矛盾是**信息不对称**：农户怕收不到钱，收购方怕收不到合格粮，双方都怕对方毁约。而传统合同审查工具的通病是——**只给结论，不给依据**。

本项目把"可信性"拆成三个可落地的技术约束：

| 约束 | 技术落点 |
|---|---|
| **可核验** | 每个抽取值带 `evidence`（原文片段）与 `confidence`；结构化事实带 `evidences` 映射 |
| **可判定** | 不停留在"相似度"，必须给出「合规 / 违规 / 缺失」这类结论 |
| **可追溯** | 每个结论都能指回具体的标准号 + 条款号 + 适用范围 |

> 这三条不是宣传语，而是贯穿数据模型的硬约束。`evidence` 字段在 `ContractField`、`ContractFacts.evidences`、`checklist` 的命中项、`compliance` 的比对项里都强制存在。

### 1.3 四个功能模块与优先级

| 模块 | 优先级 | 状态 | 职责 |
|---|---|---|---|
| 合同解析 | **P0** | ✅ 已完成 | PDF → 结构化字段（带原文依据） |
| 标准校验 | **P0** | ✅ 已完成（四层） | 条款 → 标准匹配 + 缺失检测 + 数值合规比对 |
| 企业核验 | P1 | ⬜ 未开始 | 企业名称 → 工商信息 + 交叉校验 |
| 履约模拟 | P1 | ⬜ 未开始 | 合同 + 参数 → 风险场景推演 |

### 2.2 Provider 抽象层（架构铁律）

**所有外部依赖都必须有两套以上实现，靠 `.env` 开关切换。** 业务代码不得 import 任何厂商 SDK。

| 能力 | 实现 | 就绪条件 | 说明 |
|---|---|---|---|
| LLM | `pangu` / `mock` | base_url + api_key + model | 盘古 MaaS，OpenAI 兼容 `/chat/completions` |
| OCR | `huawei` / `disabled` | AK + SK + region | 仅扫描件需要 |
| Embedding | `cloud` / `local` / `hashing` | 见下 | 三档语义能力 |
| Rerank | `cloud` / `disabled` | base_url + api_key | cross-encoder 精排 |

**Embedding 三档的定位**（这是跨机协作的关键设计）：

| 实现 | 依赖 | 语义效果 | 适用场景 |
|---|---|---|---|
| `cloud` | 仅需 API Key | 强（bge-m3，1024 维） | Windows 开发机默认 |
| `local` | torch + 2GB 权重 + 显卡 | 强（同模型本地） | Linux 主力机 |
| `hashing` | 零依赖 | 弱（字符 n-gram） | 断网兜底 / 演示保险 |

三者输出格式完全一致（**均已 L2 归一化，检索层直接用点积当余弦**），因此上层检索代码零改动。

### 2.3 配置体系

- **唯一入口**：`app/core/config.py` 的 `settings`，业务代码禁止 `os.environ`
- **路径解析**：相对路径一律经 `settings.path_of()`，以仓库根目录（`BASE_DIR`）为基准，保证任意工作目录启动都一致
- **就绪探测**：`has_pangu_credentials` / `has_ocr_credentials` / `has_cloud_credentials` / `has_enterprise_credentials`，供 `/health` 展示（**只报是否配置，绝不回显凭证内容**）

### 2.4 核心数据流

```
PDF 上传
   │
   ├─► pdf_reader.read_pdf()
   │      ├─ PyMuPDF 读文本层（电子合同，快、准、零成本）
   │      └─ 每页字符 < 20 → 判定扫描件 → 华为云 OCR 降级
   │
   ├─► structurer.structure()          【双实现：rule / llm】
   │      ├─ fields   ← 面向展示：值是原文片段 + evidence + confidence
   │      └─ facts    ← 面向推理：数值 / ISO 日期 / (指标,比较符,阈值)
   │
   ├─► storage.save_contract()         落盘 contracts/{doc_id}.json + .pdf
   │
   └─► standard_check.check_contract()
          ├─ L1 召回   store.search()  → 向量(0.5) + BM25(0.5) 混合打分
          ├─ L2 精排   reranker.rerank() → cross-encoder 对候选重排
          ├─ L3 缺失   checklist       → 必备条款覆盖检测 + 风险分
          └─ L4 合规   compliance      → 合同值 vs 标准限值 数值比对
```

## 3. 已实现能力详解

### 3.1 合同解析（P0）

#### 3.1.1 PDF 读取策略

**先便宜后昂贵**：

1. PyMuPDF 直读文本层（电子版走这条，零 API 成本）
2. 每页平均字符数 < 20 → 判定为扫描件 → 渲染 200 DPI PNG → 华为云 OCR
3. OCR 不可用时**返回明确告警**而非空结果

#### 3.1.2 双抽取器

| 抽取器 | 机制 | 适用 | 配置 |
|---|---|---|---|
| `rule` | 正则 + 关键词，多候选择优 | 格式规范的合同 | `CONTRACT_STRUCTURER=rule` |
| `llm` | 盘古大模型 + JSON 模式 + 围栏清洗 | 格式混乱、口语化 | `CONTRACT_STRUCTURER=llm` |

**两者输出同一个 `StructuredContract`**，且 `facts` 均由规则层产出——数值精度不交给模型，两条路的下游代码完全一致。

#### 3.1.3 双层数据结构（本次升级的核心）

这是系统最关键的设计：**展示层与推理层分离**。

| 层 | 字段 | 值形态 | 面向 | 示例 |
|---|---|---|---|---|
| **展示层** | `fields` | 字符串 + evidence | 人 | `"486,000元"` |
| **推理层** | `facts` | 数值 / ISO 日期 / 结构化指标 | 机器 | `486000.0` |

`ContractFacts` 完整字段：

| 字段 | 类型 | 示例值 | 解锁的下游能力 |
|---|---|---|---|
| `amount` | `Money` | `486000.0 CNY` | 违约金计算、损失推演 |
| `unit_price` | `Money` | `null`（未载明） | 价格合理性 |
| `sign_date` | `DateValue` | `2026-09-18` | 与成立日期比对（企业核验） |
| `effective_date` | `DateValue` | `kind=relative` | 生效时点风险 |
| `delivery` | `DateValue` | `2026-11-01 ~ 11-30` | 期限合理性 |
| `quantity` | `Quantity` | `180 吨` | 单位价格推算 |
| `planted_area` | `Quantity` | `320 亩` | 产能核对 |
| `deposit` | `Ratio` | `null` | 毁约风险 |
| `penalty` | `Ratio` | `rate=0.10, base=合同总金额` | **合规比对（vs 30% 上限）** |
| `payment_days` | `int` | `15` | 账期风险 |
| `payment_trigger` | `str` | `验收合格后` | 回款风险信号 |
| `quality_metrics` | `list[Quantity]` | `[水分<=14.5%, 杂质<=1.0%, 整精米率>=55%]` | **合规比对（核心）** |
| `evidences` | `dict` | 9 项原文片段 | 可追溯 |

`DateValue.kind` 的设计是刻意为之：

| kind | 含义 | 为什么重要 |
|---|---|---|
| `absolute` | 绝对日期 | 可比大小、算间隔 |
| `relative` | **相对/条件表达** | 「签字盖章之日起生效」「验收合格后15个工作日」——**本身即风险信号**，不是抽取失败 |
| `range` | 区间 | 交货期为区间是常态 |
| `none` | 未载明 | 与"写了 0"区分 |

> **判定顺序的硬约束**：`parse_date()` 必须先判 `relative` 再判 `absolute`。否则「本合同自双方签字盖章之日起生效，签订日期：2026年9月18日」会被误判为绝对日期，丢掉"生效时点不确定"这个风险信息。已有专门测试守着这条。

#### 3.1.4 数值解析能力

| 能力 | 覆盖 |
|---|---|
| 中文数字 | 财务大写（`肆拾捌万陆仟` → 486000）、日常写法（`二十`、`一百零五`） |
| 金额 | `486,000元`、`48.6万元`、`￥`/`人民币` 前缀 |
| 日期 | `2026年9月18日`、`2026-09-18`、`2026/9/18`、区间、相对表达 |
| 质量指标 | `水分含量不高于14.5%` → `(水分, <=, 14.5, %)`，支持 `不高于/不低于/不超过/不小于/≥/≤` |
| 比例 | 违约金（含基数识别「合同总金额」）、定金/预付款 |
| 账期 | `验收合格后15个工作日内` → `days=15, trigger=验收合格后` |

**黑名单机制**：违约金比例不会被误识别为质量指标（`合同总金额10%的违约金` 中的 `10%` 前无比较符，且指标名含"金额"被排除）。有回归测试守着。

### 3.2 标准校验（P0，四层能力）

这是系统的主体，从"检索"逐层升级到"判定"。

#### L1 混合召回

```
向量分 × 0.5 + 归一化 BM25 分 × 0.5
```

- 向量抓语义、BM25 抓关键词精确匹配
- 中文按字符 bigram，零分词器依赖
- 纯 Python 实现，**接口刻意做成与向量库一致的 `build / search` 形态**，换 Chroma/FAISS 时上层不动

#### L2 Cross-Encoder 精排

| 项 | 值 |
|---|---|
| 模型 | `BAAI/bge-reranker-v2-m3` |
| 候选规模 | `max(top_k × 4, 10)` |
| 失败处理 | **静默降级**回流混合排序结果，只记 warning 不抛出 |

> 精排是**增强项而非必需项**：第三方接口抖动不能让整条校验链路失败。这是容错设计的落点。

#### L3 必备条款覆盖检测

把校验方向反过来：不问"这条像哪条标准"，而问"**该有的条款，有没有**"。

清单来源：CUAD（Contract Understanding Atticus Dataset）41 类律师标注体系的**裁剪版**。

| 处理 | 内容 |
|---|---|
| 保留（通用） | 标的数量、质量标准、价格结算、交付验收、违约责任、争议解决、通知、变更解除 |
| 裁掉（美国商事特有） | Change of Control、Anti-Assignment、Non-Compete、Exclusivity |
| **补充（订单农业特有）** | 不可抗力与自然灾害免责、质量异议期与复检、价格调整机制/保底价、定金预付款、交付计量方式 |

当前清单 **14 项 = 9 项必备 + 5 项建议**，定义在 `data/standards/required_clauses.json`。

**判定方式：关键词匹配**（而非语义）。理由是**可解释性优先**——每项都会回传命中的条款序号 + 命中关键词 + 原文片段，人能复核；纯语义判断给不出可复核的依据，与本项目 `evidence` 原则相悖。

**风险评分模型**：

```
risk_score = max(0, 100 - Σ 缺失项权重)

权重：required  high=15 / medium=8 / low=4
      recommended high=6 / medium=4 / low=2
分级：≥80 低风险 ｜ ≥55 中风险 ｜ <55 高风险
```

权重写在数据文件里，调分不改代码。

#### L4 数值合规比对

**这是把"检索"彻底变成"校验"的最后一层。**

前提是标准库侧也要结构化——`data/standards/agriculture_standards.json` 升级到 v1.1，为可量化条款增加 `limits` 字段：

```json
{
  "no": "5.2",
  "title": "水分含量",
  "text": "大米水分含量应符合：籼米≤14.5%，粳米≤15.5%…",
  "limits": [
    { "metric": "水分", "op": "<=", "value": 14.5, "unit": "%", "applies_to": "籼米" },
    { "metric": "水分", "op": "<=", "value": 15.5, "unit": "%", "applies_to": "粳米" }
  ]
}
```

当前共 **31 条限值**，覆盖水分、杂质、不完善粒、碎米、整精米率、垩白度、直链淀粉、胶稠度、重金属（镉/铅/无机砷/铬）、农残（毒死蜱/三环唑/吡虫啉/氯虫苯甲酰胺）、违约金比例。

**比对判定矩阵**：

| 合同 op | 标准 op | 判定 |
|---|---|---|
| `<=` | `<=` | 合同值 ≤ 标准值 → 合规；否则**违规**（合同宽于标准） |
| `>=` | `>=` | 合同值 ≥ 标准值 → 合规；否则**违规**（合同低于标准） |
| 异向 | — | `review`（需人工核对） |
| 任意 | `range` | 落在区间内 → 合规，否则违规；合同为单边约定则 `review` |
| 单位不一致 | — | `review` |

**关键设计**：`review` 状态的存在。系统**判不了就明说判不了**，不硬给结论。三种情形走这条路：单位不一致（`%` vs `mg/kg`）、约束方向冲突、合同单边而标准是区间。

**只对"双方都有的指标"下结论**：合同没约定的指标不在此处报——那属于"缺失"，归 L3 管。一件事只有一个责任人，报告才不会自相矛盾。

## 4. 关键技术决策记录

| # | 决策 | 理由 | 代价 / 限制 |
|---|---|---|---|
| 1 | 外部依赖全部走 Provider 层 | 无凭证与有凭证两条路共用下游代码；两台机器可跑不同实现 | 多一层间接，需维护 registry 映射 |
| 2 | 向量化先用云端（SiliconFlow） | Windows 无 GPU、主力机磁盘紧张；有网即可获得强语义 | 依赖外网；合同正文发往第三方（已在 `.env.example` 标注红线） |
| 3 | 混合召回 + Cross-Encoder 精排 | 双塔模型 query/doc 互不可见，只能粗排；精排显著提升首条命中率 | 每次检索多一轮外部调用；精排失败需降级 |
| 4 | `fields` / `facts` 双层结构 | 展示要给人看（原文片段），推理要给机器算（数值）。混在一层必然二者都做不好 | 数据体积增大；两层需保持语义一致 |
| 5 | 数值走规则、语义走 LLM | 合规比对要求数值精确，LLM 会漂；条款分类等语义任务规则写不完 | 规则对格式混乱的合同召回有限 |
| 6 | 缺失检测用关键词而非语义 | 可解释、可复核，与 `evidence` 原则一致 | 会有误判（"通知"命中无关文本），故必须回传证据供复核 |
| 7 | 判不了就返回 `review` | 硬给结论会污染"可信性"这一立身之本 | 报告里会出现"待人工核对"项 |
| 8 | 标准库用 JSON 而非数据库 | Demo 阶段数据量小；零依赖、可直接编辑、便于评审查看 | 无并发控制、无版本管理 |
| 9 | 落盘用「文件夹 + JSON」 | 零依赖、可读、搬迁方便；接口形态留好换 PostgreSQL 的余地 | `doc_id` 为秒级时间戳，**同一秒上传会覆盖** |

## 5. 数据模型

### 5.1 合同

```
StructuredContract
├── contract_no / title / parties[]（Party: role, name, credit_code, contact, address）
├── amount / sign_date / effective_date / delivery_deadline
│   quality_standard / payment_terms / breach_terms     ← 展示层（字符串）
├── clauses[]（Clause: index, title, content）
├── fields[]（ContractField: key, label, value, confidence, evidence）
├── facts（ContractFacts）                              ← 推理层
└── 元信息：source_file / page_count / char_count / extractor / used_ocr
          / warnings[] / raw_text_preview
```

### 5.2 标准库（`data/standards/agriculture_standards.json` v1.1）

```
{ version, note, limits_note,
  standards: [
    { code, title, category,
      clauses: [
        { no, title, text, limits?: [{metric, op, value, upper?, unit, applies_to}] }
      ]
    }
  ]
}
```

当前规模：**6 部标准/法规 · 30 条条款 · 31 条结构化限值**

| 标准 | 类别 | 条款数 |
|---|---|---|
| GB/T 1354-2018 大米 | 产品质量 | 7 |
| GB/T 17891-2017 优质稻谷 | 品种质量 | 5 |
| GB 2762-2022 污染物限量 | 食品安全 | 4 |
| GB 2763-2021 农药残留限量 | 食品安全 | 4 |
| 粮食流通管理条例（2021修订） | 法规 | 4 |
| 农业订单合同示范文本 | 合同规范 | 6 |

### 5.3 必备条款清单（`data/standards/required_clauses.json`）

```
{ version, note,
  risk_weights: { required: {...}, recommended: {...}, levels: {...} },
  required_clauses:    [{key, name, level, risk, keywords[], advice, source}] × 9
  recommended_clauses: [同上] × 5
}
```

**刻意使用与标准库不同的顶层键名**——`loader` 只读 `standards` 键，因此清单文件即使放在同一目录也不会污染检索池（实测检索库稳定为 30 条）。

## 8. 预期最终形态

### 8.1 目标：一份《订单农业合同可信性判定报告》

系统的最终产物**不是一堆分数，而是一份可交付的判定报告**：

```
《订单农业合同可信性判定报告》
├── 一、主体核验        两家主体是否真实、是否匹配、是否自洽
├── 二、条款完整性      必备条款覆盖 X/9，缺失项清单 + 补正建议
├── 三、数值合规性      N 项指标比对，违规项 + 标准依据
├── 四、履约风险        情景推演：价格波动 / 自然灾害 / 一方违约
├── 五、综合可信度评分  0-100 分 + 等级 + 主要风险点
└── 六、证据链          每项结论 → 原文片段 + 标准条款
```

### 8.2 综合可信度评分模型（设计）

把四个模块的结论加权汇总成一个可比较的数字：

| 维度 | 数据来源 | 建议权重 | 计分方式 |
|---|---|---|---|
| 主体可信 | 企业核验 | 30% | 主体真实性 + 交叉校验通过项占比 |
| 条款完整 | checklist | 25% | 已复用 `risk_score` |
| 数值合规 | compliance | 25% | `compliant_count / total` 加权 |
| 履约风险 | simulation | 20% | 各情景损失 / 合同金额的倒数映射 |

等级：`≥85 可信` ｜ `70-84 基本可信` ｜ `55-69 存在风险` ｜ `<55 高风险`

> 权重与阈值同样写进配置文件，不硬编码。

### 8.3 企业核验（待实现）

**三层设计**：

| 层 | 内容 | 依赖 |
|---|---|---|
| **L1 本地逻辑校验** | 统一社会信用代码**校验位验算**（GB 32100-2015 加权算法，纯本地）、格式合法性、名称与代码自洽、合同内多处名称一致性 | **零依赖、零成本、可离线** |
| **L2 工商数据查询** | 名称 / 代码 / 法人 / 注册资本 / 成立日期 / 经营范围 / 经营状态 | Provider（`fixture` / 第三方 API） |
| **L3 交叉校验** | 合同主体 vs 工商登记是否一致；**成立日期 vs 签约日期**（签约时公司存在吗）；**经营范围 vs 合同标的**（粮油公司收粮、家庭农场种粮是否匹配）；经营状态是否异常 | 依赖 `facts.sign_date` |

**演示数据方案**：使用**虚构企业名 + 合规校验位的信用代码**，按结论多样性设计（正常 / 经营范围不匹配 / 已注销 / 代码造假），零法律风险且演示效果不受影响。

**Provider 设计**：新增 `enterprise_verify` provider（`fixture` | `real`），与现有 Provider 层一致。

### 8.4 履约模拟（待实现）

**输入**：合同 `facts`（金额、期限、质量标准、违约金）+ 情景参数

**三种情景**：

| 情景 | 参数 | 输出 |
|---|---|---|
| 价格波动 | 市场价涨跌幅 | 双方损益、毁约诱因分析 |
| 自然灾害 | 减产比例 | 免责范围认定、损失分担 |
| 一方违约 | 违约类型 | 违约金计算、实际损失估算 |

**技术选型建议**：盘古 LLM 做推演，**编排不必上 LangGraph**——三段情景用顺序流程 + 结构化 prompt 即可，更可控、更易调试、少一层依赖。推演的数值计算部分（违约金 = 金额 × 比例）应由 `facts` 直接算出，LLM 只负责定性分析与话术。

### 8.5 汇总判定层（待实现）

新增编排模块（如 `app/modules/judgement/`）：

- 串起「解析 → 校验 → 核验 → 模拟」

- 输出统一报告结构
- 新增接口 `POST /api/v1/contracts/{doc_id}/report`
- 支持**导出 PDF/Word**

## 10. 已知限制与技术债

### 10.1 功能性限制

| 项 | 说明 | 影响 |
|---|---|---|
| `coverage` 恒为 100% | 定义为"多少条款能匹配上任意标准"，而标准库含 6 条万金油示范条款 | 指标失真，与 `risk_score` 并列时自相矛盾。**已被 L3/L4 取代，建议替换** |
| 限值适用性不自动过滤 | 合同标的为"稻谷"还是"大米"影响适用哪条限值，系统不做判断，仅回传 `applies_to` | 同一指标可能同时报"合规"与"违规"（需人工结合适用范围判断） |
| 关键词匹配有误判 | 如"通知"可能命中无关文本 | 缺失检测会有假阳性，靠回传证据供复核 |
| 单位不自动换算 | `%` 与 `mg/kg` 无法比较 | 走 `review` 而非硬给结论 |
| 规则抽取器边界 | 对格式混乱合同召回有限 | 需切 `llm` 抽取器（未实测） |

### 10.2 工程债

| 项 | 风险 |
|---|---|
| **项目不是 git 仓库** | 无版本控制、无回滚、无备份。`.gitignore` / `.gitattributes` 已成摆设 |
| **`data/*` 被 gitignore 排除** | 一旦 `git init`，标准库与必备条款清单（**知识来源**）不会入库，换机器即丢失 |
| `doc_id` 秒级时间戳 | 同一秒上传两份合同，后者覆盖前者 |
| 无删除接口 | `data/contracts` 只增不减（测试中已累积 21 份） |
| PDF 双份存储 | 磁盘占用翻倍 |
| 同步阻塞 | `check` 含 8 条款 × 2 次外部调用，实测约 17 秒 |
| 无 RAG 评测集 | 改阈值/换模型/扩语料后**无法量化判断变好还是变坏** |

### 10.3 环境注意事项

| 项 | 说明 |
|---|---|
| 系统代理会污染本地请求 | httpx 自动读取 Windows 系统代理（本机 `127.0.0.1:7897`），连 `127.0.0.1` 的本地请求也被 `CONNECT` 隧道转发，长耗时请求（`/standards/check`）会撞代理超时被回 **502 空响应**。`.env` 里的 `HTTP_PROXY=` 无法覆盖（pydantic 不写回 `os.environ`）。测试脚本已加 `trust_env=False` 规避 |
| 云端向量化依赖外网 | 断网演示前须切回 `EMBEDDING_PROVIDER=hashing` + `RERANK_PROVIDER=disabled` |
| 合同正文发往第三方 | `EMBEDDING_PROVIDER=cloud` 时标准库语料与合同条款会发送至 SiliconFlow。敏感合同应切 `local` |

## 12. 架构铁律（开发约束）

1. **外部依赖一律走 Provider 层**；新增供应商 = 加实现类 + 在 `registry.py` 注册。业务模块不得 import 厂商 SDK
2. **业务代码禁止直接读 `os.environ`**，一律通过 `settings`
3. **相对路径必须经 `settings.path_of()` 解析**
4. **抽取值必须带证据**——`evidence` 不是可选项，"可信性"就是立身之本
5. **未就绪要显式报错**（`ProviderNotReadyError`），不静默返回空结果；空结果比报错难排查十倍
6. **模块之间不直接互相 import**，跨模块协作通过 core 层接口或上层编排
7. **数值不交给 LLM**——合规比对要求精确，语义理解才交给模型
8. **判不了就说判不了**——`review` 状态优于错误的确定结论

## 13. 总结

### 已经立住的部分

- **架构骨架完整**：Provider 抽象、集中配置、模块隔离三条铁律已落地并有实例支撑（4 类 Provider、9 种实现、3 档降级）
- **合同解析闭环**：PDF → 字段（带依据）→ 结构化事实（可推理），13 个 fact 字段覆盖金额/日期/比例/指标
- **标准校验四层**：召回 → 精排 → 缺失检测 → 数值比对，**已从"相似度检索"进化为"合规判定"**
- **验收标准严格**：48 个单测断言数值精确相等，而非"字段非空"

### 尚未立住的部分

- **两个 P1 模块是空的**（企业核验、履约模拟）——题目要求的完整性缺口
- **没有最终产物**：四个环节各自输出，缺少汇总判定层，系统尚未产出"一份报告"
- **可信性只有一半**：条款与数值的可信已实现，**主体的可信完全空白**
- **质量无法度量**：无 RAG 评测集，调整语料/阈值/模型后无法判断改善与否

### 一句话判断

> 系统的**技术骨架已经立住，且校验深度超过了常规 Demo 水平**；
> 但**功能完整性（P1 两个模块 + 汇总层）**和**工程保障（版本控制、评测集）**是当前最主要的缺口。
> 优先级建议：先做防事故项（git、doc_id、语料入库），再做数据准确性（品类识别、coverage 口径），
> 然后补齐 P1 模块并形成汇总报告。
